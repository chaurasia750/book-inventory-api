## 1. Goal

The `iam` domain exists as aggregates with all state rules inside the roots, is mapped to the `iam` PostgreSQL schema, has an initial migration, hides the system account through a query filter, and seeds the first visible Super Admin. Nothing is exposed over HTTP yet.

## 2. Out of scope

Endpoints, JWT, sessions in use (Plan 0004), password reset flow (0005), account-management use cases (0006), the system-account seeder details (0009; only the hiding filter and the column land here), UI.

## 3. Approach

**Api - Domain (`BookInventory.Domain/Iam`):**
- Enums `Role` (`SuperAdmin`, `SalesCrm`, `Accounts`, `Member`) and `AccountStatus` (`Pending`, `Active`, `Inactive`, `Suspended`, `Rejected`), stored as UPPER_SNAKE text by the platform convention.
- `AppUser : AggregateRoot` with behaviour, no public setters: `CreateStaff`, `RegisterMember(username, ..., pending|active)`, `Approve`, `Reject(reason)`, `Activate`, `Deactivate(reason)`, `Suspend(reason, until)`, `LiftSuspensionIfDue(now)`, `ChangeRole(newRole, reason)`, `UpdateProfile`, `SetPassword`, `RequirePasswordChange`, `RecordFailedLogin(now, policy)`, `RecordSuccessfulLogin(now)`, `Unlock`, `ReleaseIdentity`. Each enforces the transition table (R28) and role rules (R6), raises the events in R40, and throws `ValidationFailureException` with a message code.
- Separate roots: `UserSession`, `PasswordResetToken`, `LoginLog` (one-time `Close(reason, at)`), `UserStatusHistory`, `UserRoleHistory`.
- Normalisation helpers for username/email/mobile (R1).
- Message codes for every domain failure in one `IamMessages` constants class (R55).

**Api - Infrastructure:**
- One `ModuleEntityConfiguration` per root (schema `iam`), unique indexes on normalised username/email/mobile, `user_session(refresh_token_hash)` and `password_reset_token(token_hash)` unique, login-log indexes from spec §4, partial unique index allowing at most one `is_system_account`, foreign keys RESTRICT.
- Named EF query filter `HiddenAccount` on `AppUser` (`is_system_account = false`); helper `IgnoreHiddenAccountFilter()` used only by login lookup and seeders (R43).
- `IUserDirectory` port in Application (list/get users, always through the filter).
- `AuthOptions` (Password, Lockout, Tokens sections) bound with validation at startup (R54) - values only, used from Plan 0004.
- Migration `Iam_Initial` (schema `iam`). Generated by me and its SQL shown first; per the owner's decision I apply it to the local dev database `book_inventory` only (needs the PostgreSQL user/password as a connection string from you, not stored in the repo).
- `IamSeeder` (runs at startup): if no visible active Super Admin exists, create one from `Seed:SuperAdmin:*` (username, email, full name, password from configuration/secret store), with `must_change_password = true`; refuses to run with an empty password. Reserved usernames list (`system`, `admin`, `root`, ...) rejected by `AppUser` creation.

**Ui:** none.

## 6. Risks and notes

- Invalid-transition rules live only in the domain; later use cases must not bypass them (CLAUDE.md aggregate rules).
- The seed password comes from configuration; it must not be committed. For local dev put it in user-secrets or an environment variable. For this plan it is in the user-secrets of `BookInventory.Api` (key `Seed:SuperAdmin:Password`).
- **Follow-up for a `platform` plan:** `AddValidatedOptions` in BuildingBlocks does not recurse into nested options, so every module with grouped settings must validate itself (see AC29 above). Fixing it once in `AddValidatedOptions` is the right place; not done here because it is cross-cutting, outside this plan's module.
- The Super Admin seeder loses a startup race gracefully (see "Review follow-up"); it still relies on the unique index on `user_name` and needs no lock.
- The hidden system account is only a column, a factory and a filter in this plan. Its own seeder and its password policy (`SystemAccount:*`) are Plan 0009.
- `UserStatusHistory` and `UserRoleHistory` rows are not written automatically by the roots (that is the use-case layer's job in Plan 0006), so nothing writes them yet.
- All six roots derive from `AggregateRoot`, so the history and log tables also carry the standard audit and `row_version` columns. Approved in the spec and plan; revisit if a table grows large enough for that to matter.
