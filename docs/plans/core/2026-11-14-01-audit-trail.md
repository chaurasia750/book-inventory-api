## 1. In one minute
After this plan every committed change of an audited row leaves one entry (who, when, what, which company), and `GET /api/v1/audit` lets the Super Admin read all of them and an Owner read their own company's. Try it: create a company as Super Admin, then `GET /api/v1/audit?entityType=Company` shows a `CREATED` entry with the company's name and the Super Admin as actor.

## 2. Touches / leaves out
Touches: `BookInventory.Domain/Core` (the entry, the action enum), `BookInventory.Application/Core` (query service, the actor port, messages), `BookInventory.Infrastructure/Core` and `Persistence` (capture in `AppDbContext`, configuration, migration, markers on secret columns and on excluded entities in the existing `iam`, `core` and `company` configurations), `BookInventory.Api` (actor adapter, `AuditController`). It does not touch `library/BuildingBlocks`. Leaves out: the screens (core#02), export (AQ5) and any change of existing business rules.

## 3. Approach
`AppDbContext` overrides the save: before calling the base save it reads the change tracker, builds one `AuditEntry` per added, modified or deleted audited row (changed fields only for an update, A2) and adds them to the same save, so they commit or roll back with the change (A1). A column or an entity is excluded through a metadata annotation set in its entity configuration (`Audit:Secret`, `Audit:Ignore`), so a later migration cannot leak a new column of a marked secret entity without someone deciding (AAC10): secret columns are listed by name per entity. The actor comes from a port `IAuditActor` implemented in `Api` from the token claims (`sub`, `name`, `sys`); a job has none and is "System" (A4). The company of a row is read from its `company_id` property when it has one, from its own id for `Company`, otherwise null (A5). The read side scopes an Owner by `ICurrentCompany` and ignores a `companyId` filter from them (A7). The entry table is insert-only: the repository exposes no update or delete and the application's database role is not given them (A6). Schema change: yes (new table `core.audit_entry`). Only this plan changes the `core` schema right now.

## 7. Risks and notes
Rollback of the migration: drop `core.audit_entry` (no data exists before this plan). The audit write doubles the rows written per change; the size of `old_value` and `new_value` is bounded by writing changed fields only. The override must keep the audit columns and domain-event dispatch of the base save unchanged; the check script re-runs the iam and company checks to prove nothing else moved.
