## 1. In one minute
After this plan every committed change of an audited row leaves one entry (who, when, what, which company), and `GET /api/v1/audit` lets the Super Admin read all of them and an Owner read their own company's. Try it: create a company as Super Admin, then `GET /api/v1/audit?entityType=Company` shows a `CREATED` entry with the company's name and the Super Admin as actor.

## 2. Touches / leaves out
Touches: `BookInventory.Domain/Core` (the entry, the action enum), `BookInventory.Application/Core` (query service, the actor port, messages), `BookInventory.Infrastructure/Core` and `Persistence` (capture in `AppDbContext`, configuration, migration, markers on secret columns and on excluded entities in the existing `iam`, `core` and `company` configurations), `BookInventory.Api` (actor adapter, `AuditController`). It does not touch `library/BuildingBlocks`. Leaves out: the screens (core#02), export (AQ5) and any change of existing business rules.

## 3. Approach
`AppDbContext` overrides the save: before calling the base save it reads the change tracker, builds one `AuditEntry` per added, modified or deleted audited row (changed fields only for an update, A2) and adds them to the same save, so they commit or roll back with the change (A1). A column or an entity is excluded through attributes on the domain class itself (`[AuditSecret]` on a property, `[AuditIgnore]` on a class), next to the data they protect, so the owning module decides and a new column of a marked entity is audited unless someone marks it (AAC10). The actor comes from a port `IAuditActor` implemented in `Api` from the token claims (`sub`, `name`, `sys`); a job has none and is "System" (A4). The company of a row is read from its `company_id` property when it has one, from its own id for `Company`, otherwise null (A5). The read side scopes an Owner by `ICurrentCompany` and ignores a `companyId` filter from them (A7). The entry table is insert-only: the repository exposes no update or delete and the application's database role is not given them (A6). Schema change: yes (new table `core.audit_entry`). Only this plan changes the `core` schema right now.

## 6. Not verified
- The migration `Core_AuditEntry` (one new insert-only table with three indexes; additive) was applied only to throw-away databases. It was **not** applied to the local development database `book_inventory`; the app applies it at its next start. The SQL was shown to the owner and is waiting for confirmation.
- A6 at database level: the application connects as a superuser in this environment, so a `REVOKE UPDATE, DELETE` on `core.audit_entry` for the application role is a deployment step that was not exercised.
- A background *job* other than the startup seeder (the suspension-lift sweeper) was not triggered; the same code path (no HTTP context) was proven by the seeder.
- An anonymous request (a failed login) is recorded as "System"; the spec names only jobs and the hidden account, so this is a decision to confirm.
- Retention, partitioning and the size of the table under load were not exercised (A10).
- The regression run of the earlier checks covered `company#01` (40 of 40); the checks of `iam#03` and `company#03` were not repeated after the save override.

## 7. Risks and notes
Rollback of the migration: drop `core.audit_entry` (no data exists before this plan). The audit write doubles the rows written per change; the size of `old_value` and `new_value` is bounded by writing changed fields only. The override must keep the audit columns and domain-event dispatch of the base save unchanged; the `company#01` checks were re-run to prove nothing else moved (40 of 40).
