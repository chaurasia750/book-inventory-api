## 1. In one minute
After this plan the solution can turn an HTML string into a PDF through one shared capability: `IHtmlToPdfRenderer.RenderAsync(html, options, ct)` returns the PDF bytes, rendered by the Chromium-based browser already installed on the machine (Chrome, else Edge) in headless mode, with A4 paper, margins, a repeating header/footer and `Page x of y`. See it working with a scratch endpoint that renders a sample HTML (a repeating header and a 300-row table) into a valid PDF. No business document is built here.

## 3. Approach
One port, one implementation, chosen by configuration: `Documents:Pdf:BrowserPath` (optional; auto-detected Chrome, else Edge) and `Documents:Pdf:TimeoutSeconds`. The renderer launches the browser headless, loads the HTML, and calls `Page.printToPDF` with `paperWidth/paperHeight` A4, `printBackground: true`, margins, `displayHeaderFooter: true` and the header/footer templates, so the header repeats and `Page x of y` is filled by the browser (`span.pageNumber`/`span.totalPages`) (P25). The choice of how it talks to Chromium is PQ3: recommended **PuppeteerSharp** with `ExecutablePath` set (so it never downloads), alternative a minimal CDP client over `ClientWebSocket`. A missing browser, a launch failure or a render failure raises the domain exception `document.render_failed` (`500`) and leaves no file behind (P25, AC20). No new table; nothing is stored.

## 7. Risks and notes
A new package (PuppeteerSharp, PQ3) needs approval; the port hides it, so swapping to a hand-written CDP client later changes nothing outside BuildingBlocks. The server needs Chrome or Edge installed (PQ2). The browser is launched per render in Phase 1 (simple, correct); a pooled browser is a later optimisation if it ever matters.
