## 1. In one minute
After this plan `GET /api/v1/receipts/{id}/pdf` answers an A5 PDF receipt with the company logo, the modes, the total in words and the invoices it paid.

## 2. Touches / leaves out
Touches: the `payment` module (a PDF model builder and an embedded A5 template, one endpoint), reusing the template renderer, the HTML-to-PDF renderer and the company identity capability (no new package). No schema change.
Leaves out: the screen button (payment#08).

## 3. Approach
Same shape as the invoice PDF: a model of pre-formatted, HTML-encoded values filled into a Scriban template and rendered by the existing browser renderer; the amount in words reuses the sales helper; a cancelled receipt gets a CANCELLED mark.

## 4. Tasks (at most 8)

- [x] 3. The endpoint and its roles; build at 0 warnings.

## 6. Not verified
No schema change. The company of the test data has no address, contact, GSTIN, bank account or signature filled, so those parts of the receipt (header lines, "Bank account", the signature image) were not seen with data; the template prints each only when it is set (the model is the live company identity, like the invoice PDF). The footer block (bank and signatory) follows the content instead of sitting at the page bottom. A receipt with many allocations that runs onto a second page was not tried. The A5 page size is set per document in the module (the platform options default to A4). The default `dotnet build book-inventory.slnx` (blocked by the owner's running API): the API project was built into a scratch folder: 0 warnings, 0 errors. The test receipts of this check were cancelled; the test school was deactivated.
